AI-Assisted Documentation Pipeline

Two documentation-production architectures for the same problem: A human-reviewed two-agent workflow on Microsoft Copilot, now in team production, and an automated file-based pipeline on Claude Cowork, run as a personal experiment.

Both were built to move a writer’s attention off transcription and formatting and onto judgment. The measured outcome: The Copilot pipeline raised team drafting throughput from 40 to 93 drafts per week (233% of baseline, four active writers), and the Claude Cowork experiment turned 22 source documents into 63 QA-validated articles in a one-week solo sprint.

The problem

Writers were spending their best hours on the lowest-judgment work in the job. Long, unstructured source material required manual drafting, restructuring, and formatting before it could ship as review-ready documentation, and output quality varied run to run, so consistency depended on individual discipline rather than on the system. Source material arrived in many forms:

  • Training decks.
  • Transcripts.
  • SME notes.
  • Existing articles.
  • Image-only files.
  • Table-heavy PDFs.
  • Code samples.

Downstream, writers and SMEs spent review time correcting structure and format, and filling gaps where a draft missed or misread source content, before they could even validate technical accuracy. That review time is the team’s scarcest resource, spent on rework instead of judgment.

Constraints

  • Variable source. Source material varied wildly in structure, cleanliness, and format.
  • Fixed template. Output had to follow a fixed internal template, not free-form generation.
  • No silent invention. Missing, conflicting, or uncertain source information had to surface as an SME flag, never get silently invented.
  • Two-stage QA. QA needed draft QA and render/DOCX QA, not one pass at the end.
  • License ceiling. The Copilot workspace ran on a limited license (initially free-tier, no Copilot Studio access), which ruled out a fully automated agent-to-agent chain regardless of design preference.
  • Traceable runs. Every run needed a traceable log.

The approach

Copilot pipeline: Two agents, one human checkpoint

KM Drafter handles the drafting stage:

  • Takes in source material.
  • Identifies distinct user goals.
  • Proposes a parent/child document structure.
  • Converts long source into task-focused Markdown drafts against a fixed output contract.
  • Flags gaps and conflicts inline rather than inventing content.

A human reviews that draft. KM Format Editor then takes the approved Markdown and generates the DOCX.

The Format Editor applies the template, heading levels, procedures, tables, fonts, and styles against named styles, not chosen by the model.

(Chat output can’t carry visual formatting and can’t touch a Word document directly. That’s the whole reason the Format Editor exists as its own stage.)

Claude Cowork pipeline: Automated run, human gates preserved

A 13-stage file-based pipeline (intake validation → source inventory → extraction → draft planning → parent/child decomposition → draft generation → draft QA → revision → DOCX generation → render QA → logging → packaging → archiving) runs with exception-based review.

Two things stop the run for a human decision:

  • Two consecutive failures on one file.
  • A source spanning multiple topics.

Author review and SME validation still gate publication outside the run. Automating the draft doesn’t touch those checkpoints.

Key decisions

Split one agent into two, rather than debug it in place

Version one combined drafting and formatting instructions in a single agent, and it degraded unpredictably.

  • Rules dropped at random. Different rules dropped on every run once roughly 60 competing rules hit an 8,000-character instruction ceiling.
  • One job per agent. Splitting the roles gave each agent an instruction budget for behavior only.
  • Lookup data left the prompt. Static lookup data moved into reference material instead of the prompt.

Consequence An extra handoff stage, but predictable output.

Take visual styling out of the agent entirely

Asking a model to apply an exact font, size, and hex color is asking for a deterministic result by probabilistic means. The result is a permanent failure rate that prompt tuning doesn’t remove.

Styling now runs against named template styles instead.

Consequence The agent’s job narrows to structure and judgment; formatting became code’s job in both pipelines.

Keep the human checkpoint instead of a fully automated Copilot chain

Two reasons:

  • Errors reached SME review. An early pilot let an uninterrupted chain pass errors to SME review undetected.
  • No licensed handoff. The license had no path to a governed automated handoff anyway.

Consequence The Copilot pipeline trades speed for review control; the Claude Cowork pipeline later automated the run itself while keeping the same lifecycle gates outside it.

Results

Design intent: The system was built for writers, to move their attention off transcription and formatting and onto judgment. Throughput is the measurable outcome, not the goal that shaped the design. SME flagging was added on top of that, marking what actually needs verification so neither the writer nor the reviewer carries the whole document at the same level of suspicion.

Not claimed: Reduced backlog age, faster onboarding, improved review turnaround, or “publication-ready” status for the Claude pipeline’s output (QA-validated is the accurate term).

What changed after testing

  • Split the overloaded agent. KM Drafter and KM Format Editor replaced it after the stochastic rule-dropping failure.
  • Moved static lookup data out of instructions. Label sets, templates, and table specs now live in reference material the agent consults.
  • Removed styling from the agent. Visual styling left the agent’s job entirely, and code now applies it deterministically in both pipelines.
  • Kept the human checkpoint. The handoff between drafting and formatting stayed manual on Copilot rather than automated, given the license constraint and the undetected-error pilot.
  • Built exception-based stops. Repeated failure and multi-topic source halt the Claude Cowork run, instead of a checkpoint at every stage.

Limitations and next step

Limits on the Claude Cowork result

  • A sprint, not a rate. It is a personal, one-week build-and-run sprint, not a steady-state weekly rate.
  • No matched comparison. It hasn’t been compared against the Copilot pipeline under matched conditions.
  • No formal cost figure. Operating cost (token use) for the Claude pipeline wasn’t formally measured.

Next step

A controlled team trial of the Claude Cowork pipeline, measuring editing time, SME correction rate, cost, and throughput against the Copilot baseline.
