AI-Assisted Documentation Pipeline

Two documentation-production architectures for the same problem: A human-reviewed two-agent workflow on Microsoft Copilot, now in team production, and an automated file-based pipeline on Claude Cowork, run as a personal experiment. The Copilot pipeline raised team drafting throughput from 40 to 93 drafts per week — 233% of baseline, four active writers. The Claude Cowork experiment turned 22 source documents into 63 QA-validated articles in a one-week solo sprint.

01 — The problem

The problem

Long, unstructured source material — training decks, transcripts, SME notes, existing articles, image-only files, table-heavy PDFs, code samples — required manual drafting, restructuring, and formatting before it could ship as review-ready documentation. Writers and SMEs spent review time correcting structure and format, and filling gaps where a draft missed or misread source content, before they could even validate technical accuracy. That review time is the team’s scarcest resource, spent on rework instead of judgment.

02 — Constraints

Constraints

  • Source material varied wildly in structure, cleanliness, and format.
  • Output had to follow a fixed internal template — not free-form generation.
  • Missing, conflicting, or uncertain source information had to surface as an SME flag, never get silently invented.
  • QA needed two stages — draft QA and render/DOCX QA — not one pass at the end.
  • The Copilot workspace ran on a limited license (initially free-tier, no Copilot Studio access), which ruled out a fully automated agent-to-agent chain regardless of design preference.
  • Every run needed a traceable log.
03 — The approach

The approach

Copilot pipeline — two agents, one human checkpoint

KM Drafter takes in source material, identifies distinct user goals, proposes a parent/child document structure, and converts long source into task-focused Markdown drafts against a fixed output contract — flagging gaps and conflicts inline rather than inventing content. A human reviews that draft. KM Format Editor then takes the approved Markdown and generates the DOCX: Template, heading levels, procedures, tables, fonts, and styles applied against named styles, not chosen by the model. (Chat output can’t carry visual formatting and can’t touch a Word document directly — that’s the whole reason the Format Editor exists as its own stage.)

Claude Cowork pipeline — automated run, human gates preserved

A 13-stage file-based pipeline (intake validation → source inventory → extraction → draft planning → parent/child decomposition → draft generation → draft QA → revision → DOCX generation → render QA → logging → packaging → archiving) runs with exception-based review: Two consecutive failures on one file, or a source spanning multiple topics, stop the run for a human decision. Author review and SME validation still gate publication outside the run — automating the draft doesn’t touch those checkpoints.

04 — Key decisions

Key decisions

Split one agent into two, rather than debug it in place. Version one combined drafting and formatting instructions in a single agent. It degraded unpredictably — different rules dropped on every run once roughly 60 competing rules hit an 8,000-character instruction ceiling. Splitting the roles gave each agent an instruction budget for behavior only; static lookup data moved into reference material instead of the prompt. Consequence: An extra handoff stage, but predictable output.

Take visual styling out of the agent entirely. Asking a model to apply an exact font, size, and hex color is asking for a deterministic result by probabilistic means — a permanent failure rate that prompt tuning doesn’t remove. Styling now runs against named template styles instead. Consequence: The agent’s job narrows to structure and judgment; formatting became code’s job in both pipelines.

Keep the human checkpoint instead of a fully automated Copilot chain. An early pilot let an uninterrupted chain pass errors to SME review undetected, and the license had no path to a governed automated handoff anyway. Consequence: The Copilot pipeline trades speed for review control; the Claude Cowork pipeline later automated the run itself while keeping the same lifecycle gates outside it.

06 — What changed after testing

What changed after testing

  • Split the single overloaded agent into KM Drafter and KM Format Editor after the stochastic rule-dropping failure.
  • Moved static lookup data (label sets, templates, table specs) out of instructions and into reference material the agent consults.
  • Removed visual styling from the agent’s job entirely — code now applies it deterministically in both pipelines.
  • Kept the human checkpoint between drafting and formatting on Copilot rather than automating it, given the license constraint and the undetected-error pilot.
  • Built exception-based stops (repeated failure, multi-topic source) into the Claude Cowork run instead of a checkpoint at every stage.
07 — Limitations and next step

Limitations and next step

The Claude Cowork result is a personal, one-week build-and-run sprint, not a steady-state weekly rate, and it hasn’t been compared against the Copilot pipeline under matched conditions. Operating cost (token use) for the Claude pipeline wasn’t formally measured. Next step: A controlled team trial of the Claude Cowork pipeline, measuring editing time, SME correction rate, cost, and throughput against the Copilot baseline.
